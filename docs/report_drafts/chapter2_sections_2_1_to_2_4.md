## 2.1 Chapter Introduction

This chapter reviews the literature that provides the conceptual and empirical context for the dissertation. Its purpose is to establish how the problem examined in later chapters—the reliability of npm package references in LLM-generated Node.js code—relates to existing research on LLM-assisted software development, code hallucination, software dependency ecosystems, and software supply-chain security. The review does not introduce empirical findings from the present study. Rather, it sets out the concepts, distinctions, and methodological considerations on which the study's design and interpretation depend, and it identifies the respects in which the existing literature informs, and bounds, what an empirical assessment of generated dependency references can reasonably claim.

The review proceeds from the general to the specific. It begins with the use of Large Language Models (LLMs) for code generation and with the reliability limitations that the literature associates with generated code, including the phenomenon described as code hallucination (Section 2.2). It then turns to the external environment on which generated code frequently depends: reusable third-party packages, the package managers that retrieve them, and the public registries through which they are distributed (Section 2.3). Because this environment is also a recognised surface for software supply-chain attacks, Section 2.4 examines threats that operate through package names, such as typosquatting and dependency confusion, and distinguishes them from errors in which no adversary is involved. The subsequent sections narrow the focus further to package hallucination in LLM-generated code and to slopsquatting as a downstream security concern (Section 2.5), before considering validation and classification approaches, reliability and risk, the dimensions along which prior studies differ, and the resulting research gap.

Two boundaries apply throughout. First, the literature reviewed here spans several programming languages and package ecosystems, and some of the most relevant studies were conducted outside the npm ecosystem. Such work is treated as context: the empirical study reported in this dissertation was confined to Node.js and the npm registry, and cross-ecosystem literature is not presented as evidence about ecosystems that the study did not examine. Second, the security literature discussed in this chapter describes attacks and attack scenarios that the present study did not perform, simulate, or observe. These concepts are reviewed because they clarify why unreliable dependency references matter and how they should be distinguished from one another, not because the dissertation evaluated them experimentally. Within these boundaries, the chapter aims to provide a bounded synthesis of the literature rather than an exhaustive survey of every related field.

## 2.2 Large Language Models in Software Development

### 2.2.1 Code generation and reliability limitations

LLMs are now widely discussed in software-engineering research as tools that can generate source code, complete partially written programs, and propose implementations from natural-language descriptions of a task. Hallucinations in LLM-generated code have become the subject of a dedicated systematic literature review [Gao et al., 2025], alongside broader systematic reviews of hallucination in LLMs generally [Woesle et al., 2025]. The existence of such reviews indicates that the reliability of generated code is treated as an established research concern. It also suggests that code-oriented hallucination may be understood as a domain-specific manifestation of a wider phenomenon, while retaining characteristics that are particular to software, such as the requirement that generated code compile, execute, and interact correctly with external libraries and interfaces.

The studies reviewed here do not characterise generated code as uniformly unreliable. Their emphasis falls instead on the observation that the plausibility of generated code is not a sufficient indicator of its correctness. Tian et al. (2025) note that code produced by LLMs can be syntactically correct and superficially plausible while nevertheless failing to execute or to satisfy the requirements of the task, and they propose execution-based verification in response. Liu et al. (2026) similarly frame hallucination as a concern that extends beyond functional correctness, developing an empirical categorisation of hallucinations in LLM-generated code. Taken together, these studies suggest that the evaluation of generated code cannot rely solely on whether the output appears well formed, and that the kind of check applied determines which kinds of error can be observed.

A related theme concerns the structure of software itself. Code differs from ordinary prose in that it must conform to formal syntax, reference identifiers defined elsewhere, and operate within the constraints of a particular language, runtime, and set of libraries. Related work has examined the implications of not treating code as natural language for repository-level code generation [Le-Anh et al., 2026], and other work has examined the identification and mitigation of API misuse by LLMs [Zhuo et al., 2025]. These strands of research are noted here as context. Their relevance to the present study lies in a more general observation: generated code frequently depends on entities outside the immediate text of the response—files, interfaces, and libraries—whose existence and behaviour cannot be confirmed from the generated output alone.

The probabilistic character of generation adds a further consideration. Spracklen et al. (2025), in their analysis of package hallucinations by code-generating LLMs, state that probabilistic generation contributes to diversity in model outputs, and their study examined both the repetition of outputs and the effect of varying the sampling temperature. The broader implication for empirical work is methodological: a single generated response to a task provides limited evidence about how a model behaves on that task, because a repeated request under the same conditions may yield a different response. Studies that seek to characterise the reliability of generated code therefore need to consider repetition, fixed generation conditions, and the preservation of the specific outputs from which conclusions are drawn. This consideration is revisited in Section 2.8, where the dimensions along which prior empirical studies differ are compared.

Reliability concerns also bear on debugging and verification. Where generated code contains errors that are not evident from its surface form, the burden of detecting those errors shifts towards review, testing, and other forms of validation external to the model. Related work has examined approaches intended to make LLM-based coding more reliable, trustworthy, and explainable for production systems [Dubey and Madisetti, 2026]. The execution-based and review literature discussed above [Tian et al., 2025; Gao et al., 2025] indicates that validation of generated code is an explicit activity with its own design choices, rather than a property that can be assumed from the generating model. That point frames the treatment of hallucination in the following subsection.

### 2.2.2 Code hallucination as a software-engineering concern

Chapter 1 adopted a study-specific working definition of hallucination as generated software output presented as valid but not supported by the relevant external reality. The reviewed studies do not converge on a single universal definition of *code hallucination*. Gao et al. (2025) review the characterisation of code hallucinations in LLMs, together with proposed causes, detection and evaluation approaches, mitigation methods, and open challenges, and their review illustrates that the concept is applied to a range of errors rather than to one precisely bounded phenomenon. Liu et al. (2026) contribute an empirical categorisation of hallucinations in generated code, and related work has examined hallucinations in LLM-generated code more generally [Agarwal et al., 2024] as well as security-related code hallucinations specifically [Daoud, 2026]. The general literature on LLM hallucination provides a wider conceptual backdrop [Woesle et al., 2025], but it does not by itself define what counts as a hallucination in code or in a dependency reference.

Two points recur across the studies whose full findings are discussed here [Gao et al., 2025; Liu et al., 2026; Tian et al., 2025]. The first is that hallucination in code is a reliability concern: it affects whether a generated solution can be used as supplied. The second is that hallucinated content may not be evident from surface inspection, because generated code can be syntactically correct and plausible while failing to execute or to satisfy the task requirements [Tian et al., 2025]. The sources differ, however, in emphasis and in the validation method through which hallucination is operationalised. A systematic review such as that of Gao et al. (2025) organises the field conceptually; an empirical categorisation such as that of Liu et al. (2026) derives categories from observed generated code; and an execution-based approach such as that of Tian et al. (2025) identifies hallucination through the behaviour of code when it is run. These differences are not merely presentational. The method used to detect hallucination determines which errors become visible: an execution-based check can reveal behavioural failures that a syntactic check would miss, whereas an error that consists of referring to an external entity that does not exist may require evidence from outside the code altogether.

This last category is of particular relevance to the present dissertation. A generated program may be internally consistent and syntactically well formed while referring to a library, interface, or package whose existence depends on an external source of truth. The validity of such a reference cannot be established from the generated text alone; it requires comparison with the relevant documentation, index, or registry. Research on library hallucinations in LLM-generated code has examined this class of error in the setting of developer queries [Twist et al., 2026], and research on package hallucination has examined the case in which the external entity is a package distributed through a public registry [Spracklen et al., 2025]. These studies are considered in detail in Section 2.5. For the present discussion, their significance is conceptual: they show that one form of code hallucination is located not in the logic of a program but in its dependencies.

The literature on code hallucination therefore supplies three considerations that carry forward into the remainder of this chapter. First, because no single definition is universally adopted, any empirical study must state its own operational definition and the evidence required to apply it. Second, the choice of validation method shapes what can be measured, so that results obtained under one method are not straightforwardly comparable with results obtained under another. Third, a subset of code hallucinations concerns references to external components, whose assessment depends on the state of an external system. The next section examines that external system—software dependency ecosystems and package registries—before Section 2.4 considers the security threats that operate through package names.

## 2.3 Software Dependency Ecosystems and Package Registries

### 2.3.1 Dependencies and the software supply-chain context

Contemporary software development relies extensively on reusable components that are developed and maintained by parties other than the developer who uses them. Rather than implementing every capability directly, developers commonly incorporate open-source libraries and frameworks that provide functionality such as network communication, data parsing, authentication, or testing. This practice supports productivity and reuse, but it also means that a software product depends on code that its developers did not write and may not have reviewed. The software supply-chain security literature treats this relationship as a security-relevant dependency in its own right: open-source dependencies and components constitute a context through which attacks on downstream software can be attempted [Ladisa et al., 2023; Williams et al., 2025].

The literature approaches this context at different levels of abstraction. Ladisa et al. (2023) systematise attacks on open-source software supply chains in the form of a taxonomy. Williams et al. (2025) set out research directions in software supply-chain security and identify dependencies as one of the vectors through which such attacks can occur. Duan et al. (2020) take a more empirical, ecosystem-focused perspective, measuring supply-chain attacks on the package managers of interpreted languages. Although these works differ in method—taxonomic synthesis, research agenda, and empirical measurement respectively—they agree that the mechanisms by which third-party components are obtained are a meaningful object of security analysis, and not merely a matter of development convenience. Related work has also systematised the practical detection of software supply-chain attacks [Ohm and Stuke, 2023], and a research agenda has applied the supply-chain perspective to LLMs themselves [Wang et al., 2025].

For the purposes of this dissertation, the significance of the supply-chain literature is twofold. First, it indicates that a dependency is not a neutral detail of an implementation: the choice of which external component to rely upon has consequences for the reliability and security of the resulting software. Second, it indicates that the consequences of a dependency choice depend on the surrounding context, including the registry from which the component is retrieved, the controls applied before it is installed, and the behaviour of other actors in the ecosystem [Ladisa et al., 2023; Williams et al., 2025]. This contextual dependence is important because it cautions against treating any single dependency-related observation as evidence of compromise. A dependency reference is an instruction to obtain a component; whether acting on that instruction leads to a reliability failure, a security incident, or neither depends on conditions beyond the reference itself.

The supply-chain literature is also broader than the question of whether a named dependency exists. The taxonomic and research-agenda work cited above addresses attacks on open-source software supply chains in general, rather than package names specifically. The present dissertation does not examine these wider threats. It draws on the supply-chain literature for a narrower purpose: to explain why the validity of a package name in generated code is relevant beyond the immediate correctness of the program, and to situate package-name errors within a recognised field of security research without implying that such errors are themselves attacks.

### 2.3.2 Package managers, registries, and npm as one ecosystem

Package managers are the tools through which dependencies are declared, resolved, and retrieved. In a typical workflow, a developer or build process specifies the name of a required package—and, optionally, a version—and the package manager resolves that name against one or more registries, downloads the corresponding artefact, and makes it available to the project. The package name is therefore the key through which the developer's intention is connected to a specific component published by a specific party. This arrangement has an important consequence: the meaning of a dependency declaration is not contained within the declaration itself but is determined by the state of the registry at the time the name is resolved. A name that resolves to a legitimate, maintained package at one time may resolve differently, or not at all, at another.

Public registries serve large communities of publishers and consumers, and the security literature has examined them as points at which malicious or unwanted components can enter the software supply chain. Duan et al. (2020) analysed supply-chain attacks on package managers for interpreted languages, examining how registries can be abused to distribute malicious packages, and developed an analysis approach that combined metadata, static, and dynamic analysis to identify such packages. Their work illustrates that registry-level analysis can draw on several forms of evidence, and that the presence of a package in a registry does not in itself establish that the package is benign. Spracklen et al. (2025) make a related point in the context of package hallucination: a package name that exists in a registry is not thereby shown to be safe, because existence and trustworthiness are different properties. Conversely, as Section 2.4 discusses, a name that is absent from a registry may be absent for more than one reason.

Registry evidence also plays a central role in empirical research on package hallucination, because it provides an external reference against which generated package names can be compared. Spracklen et al. (2025) cross-referenced package names produced by code-generating LLMs against registry information in their evaluation of both Python and JavaScript code generation. Such work indicates that registry comparison is a recognised means of gathering evidence about generated dependency references. It does not, however, establish that registry comparison alone is sufficient to classify every reference, a question that Section 2.6 examines in relation to validation and classification approaches.

Within this broader landscape, npm is the package ecosystem associated with the Node.js runtime and is one of several language-specific ecosystems examined in the literature. It is the ecosystem to which the empirical work of this dissertation was confined. Because npm package names may be scoped, imports may refer to subpaths within a package, and generated code may also refer to Node.js built-in modules or local files, the text of a generated import or installation instruction cannot simply be equated with an npm package name. The specific normalisation rules applied in this dissertation are described in Chapter 3.

The selection of npm for the empirical study should not be read as a claim that npm is uniquely vulnerable, or that its design explains outcomes differently from other ecosystems. Cross-ecosystem literature—including package-hallucination research spanning Python and JavaScript [Spracklen et al., 2025] and measurement of supply-chain attacks across interpreted-language package managers [Duan et al., 2020]—provides useful context for understanding registries in general. However, the literature reviewed in this chapter does not provide evidence on which to base causal claims about how particular registry naming or publication policies determine the frequency of package-name errors. Such claims are therefore not made in this chapter. The present dissertation treats npm as a single, well-defined registry context within which package references can be examined consistently, and it leaves comparisons across ecosystems outside its empirical scope.

The dependence of a package reference on external registry state has a methodological implication that connects this section to the next. Because a dependency declaration is resolved by name, errors in the name—whether accidental, adversarially induced, or generated by a model—are consequential. They may cause installation to fail, may cause a different component from the one intended to be retrieved, or, in some circumstances, may create an opportunity for a third party to supply a component under the erroneous name. The security literature has examined several of these possibilities as distinct threats that operate through package names. Section 2.4 reviews those threats and distinguishes them from the phenomenon of package hallucination.

## 2.4 Software Supply-Chain Threats Related to Package Naming

Because package managers resolve dependencies by name, package names constitute an attack surface within the software supply chain. Several attack techniques discussed in the literature exploit the gap between the package a developer intends to use and the package that a name actually resolves to. This section reviews two techniques that the reviewed literature distinguishes explicitly, typosquatting and dependency confusion, and then considers the broader set of package-manager threats and the distinctions between accidental dependency errors, adversarial package naming, and hallucinated package names. The aim is not to survey supply-chain attacks comprehensively, but to establish conceptual boundaries that prevent package hallucination from being conflated with established attack techniques.

### 2.4.1 Typosquatting

Typosquatting is a package-naming attack in which an adversary publishes a package under a name that closely resembles the name of a legitimate package, in the expectation that some users will install the malicious package by mistake. Al-Zofi (2025) characterises typosquatting as a similar-name attack rooted in human error, in which developers mistype or misread the name of the package they intend to install. Spracklen et al. (2025) likewise treat attacks based on similar names as a form of package confusion, and they discuss such attacks separately from the case in which a generated package name is fictitious. The defining features of typosquatting are therefore intentional adversarial registration and resemblance to an existing legitimate name: the attack depends on the legitimate package being known and on a plausible error in reproducing its name.

This characterisation has two implications for the analysis of generated dependency references. First, typosquatting presupposes a legitimate target. A generated package name that closely resembles a real package may reflect an error related to that real package—for example, an incorrect spelling or an inaccurate recollection of its name—rather than the invention of an entirely new package. Such cases may be better understood as name confusion than as fabrication, and they are relevant to classification because they have a different relationship to the ecosystem from a name with no legitimate counterpart. Second, resemblance alone does not establish that an attack has taken place. A mistyped or confused name in generated code is an error in the output; it acquires security significance only if an adversary has registered the resembling name and a user or automated process retrieves the resulting package. The literature on typosquatting therefore informs how name similarity should be interpreted, but it does not justify treating every similar-looking name as malicious.

### 2.4.2 Dependency confusion

Dependency confusion operates through package resolution rather than through visual resemblance. Al-Zofi (2025) describes it as an attack in which an adversary registers, on a public registry, a package bearing the name of a package that an organisation uses internally, so that package resolution selects the public version rather than the intended internal one. The attack exploits the way in which resolution behaviour selects between package sources or namespaces, and it can succeed even when the dependency name is written exactly as intended, because the vulnerability lies in which source the name is resolved against.

Dependency confusion is thus conceptually distinct both from typosquatting and from package hallucination. It does not depend on a mistyped name, and it does not depend on a model generating an invented name; it depends on the existence of a legitimate internal name and on resolution behaviour that can be influenced by public registration. Direct support for this definition within the reviewed literature comes from Al-Zofi (2025), and the concept is included here to clarify the boundaries of package-naming threats rather than as a phenomenon examined empirically in this dissertation. Its relevance to the analysis of generated code is limited but instructive. A generated reference to a package name that is not found on a public registry does not, in itself, indicate dependency confusion; it may also reflect a name that was never published, a name associated with a private or local context, or an error in the name. Treating such observations as evidence of dependency confusion would attribute an adversarial mechanism to what may be a non-adversarial error.

### 2.4.3 Related package-manager threats and the distinction from package hallucination

Typosquatting and dependency confusion are two instances of a wider class of threats that exploit package managers and registries. Duan et al. (2020) measured supply-chain attacks on package managers for interpreted languages, examining the distribution of malicious packages through registries and analysing such packages using combined metadata, static, and dynamic evidence. The taxonomy of Ladisa et al. (2023) and the research agenda of Williams et al. (2025) place attacks involving dependencies within a broader landscape of threats to open-source software supply chains. Because these works address software supply-chain attacks at a broader level than package naming, they indicate that the threat landscape extends beyond the naming-based techniques reviewed in Sections 2.4.1 and 2.4.2. They also indicate that the consequences of any particular dependency error depend on context—on which package is retrieved, by whom, under what controls, and with what subsequent behaviour [Ladisa et al., 2023; Williams et al., 2025].

Against this background, it is possible to distinguish three categories that are sometimes discussed together but differ in origin and implication. The first is *accidental dependency error*: a developer or tool, which may include an LLM, cites an intended legitimate package incorrectly—for example, by using an outdated name, the wrong scope, or a misremembered spelling—without any adversary being involved. The second is *adversarial package naming*: an attacker deliberately arranges for a name to resolve to a malicious component, as in typosquatting or dependency confusion. The third is *package hallucination*: Spracklen et al. (2025) use the term for the case in which generated code recommends or references a package that does not exist, and Zhao et al. (2025) similarly describe LLMs recommending non-existent packages. Package hallucination is thus defined by two features—the name originates in model output, and the referenced package does not exist—rather than by the actions of an attacker. The boundary between the first and third categories is not always evident from the name alone, because model output may also contain mis-scoped or misspelled references to real packages; how this boundary was operationalised in the present study is described in Chapter 3.

The literature also describes a downstream scenario that connects package hallucination to adversarial naming. *Slopsquatting* refers to the malicious registration of package names that LLMs hallucinate, so that a user who acts on a hallucinated reference may retrieve a package supplied by an attacker [Al-Zofi, 2025]. Spracklen et al. (2025) present a comparable package-confusion attack scenario in which the adversary registers a hallucinated name and a user subsequently installs the package. In both accounts, the attack depends on conditions additional to the hallucination itself: an adversary must register the name, and a user or automated process must act on the generated reference. A hallucinated package name is therefore not equivalent to an attack or to a compromise; it is a reliability defect that may acquire security significance if those further conditions are met. Slopsquatting is considered in more detail in Section 2.5.

These distinctions have direct consequences for how empirical observations of generated dependency references should be interpreted. An observation that a generated package name does not resolve in a registry is compatible with several explanations: the name may never have been published, it may be a mis-scoped or misspelled form of a real package, it may refer to a package that existed previously, or it may denote a local module rather than an external dependency. Only the first of these corresponds straightforwardly to package hallucination as defined in the literature, and none of them, on its own, constitutes an attack. Equally, the fact that a generated name does resolve to a published package does not establish that the package is the one intended or that it is safe [Spracklen et al., 2025]. The naming-threat literature therefore reinforces the need, identified in Section 2.2.2, for explicit operational definitions and for classification procedures that separate distinct failure mechanisms rather than combining them under a single label.

It should be emphasised that the concepts reviewed in this section serve an interpretive function in this dissertation. Section 2.5 turns from these naming threats to the empirical literature on package hallucination itself.
