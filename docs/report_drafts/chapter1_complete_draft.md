## 1.1 Chapter Introduction

Large Language Models (LLMs) can generate source code, recommend libraries, and propose complete implementations from natural-language task descriptions. This capability changes the context in which software is constructed and reviewed, because generated code may appear correct while containing errors that are not evident from its surface form. The literature recognises such errors as code hallucinations and identifies them as a concern for the correctness, maintainability, and security of generated software [Gao et al., 2025]. More broadly, hallucination is a subject of systematic review in research on LLMs [Woesle et al., 2025].

Within this wider reliability problem, references to external software packages occupy a distinctive position. A generated solution that names a third-party dependency does not merely contain a statement about program logic; it directs the developer, or a build process, to obtain a component from a public package registry. If the named package does not correspond to a legitimate, resolvable package, the error concerns not only the generated code but also the dependency on which that code relies. Research on package hallucination has examined this intersection between LLM package recommendations and public registries [Spracklen et al., 2025; Al-Zofi, 2025]. The present dissertation examines the problem empirically within the Node.js runtime and its npm package ecosystem. It assesses explicit npm package references in LLM-generated responses to standardised Node.js coding tasks, distinguishes conservatively confirmed package-name hallucinations from broader exact-name dependency-resolution failures, and applies a rule-based practical-risk assessment to eligible confirmed findings. Although the dissertation title refers broadly to fake APIs and libraries in AI-generated code, the empirical investigation reported here is deliberately narrower, and this chapter establishes that boundary explicitly.

The chapter is organised as follows. Section 1.2 presents the background of the study, moving from LLM-assisted software development to package-name hallucination and the Node.js/npm setting in which the empirical work was conducted. Section 1.3 states the research problem, and Section 1.4 identifies the research gap addressed. Sections 1.5 to 1.7 set out the research aim, objectives, and research questions. Section 1.8 defines the scope and delimitations of the study, Section 1.9 outlines its intended contributions, Section 1.10 describes the structure of the dissertation, and Section 1.11 summarises the chapter.

## 1.2 Background of the Study

The integration of LLMs into software engineering has altered the way in which code is constructed, debugged, and verified. In conventional programming workflows, verification depends on deterministic test suites, manual code review, and human oversight. AI-assisted programming, by contrast, introduces non-deterministic generated code that requires continuous trust calibration and validation [Liu et al., 2026]. The need for reliable and explainable approaches to debugging such code has been emphasised particularly for production environments, where the opacity of the underlying models complicates the isolation of errors [Dubey and Madisetti, 2026]. These developments do not imply that generated code is inherently less reliable than manually written code; rather, they indicate that its reliability cannot be assumed from its fluency and must be assessed through evidence external to the model output.

For the purposes of this dissertation, *hallucination* denotes generated software output presented as valid or factual but not supported by the relevant external reality, including the languages, libraries, registries, and interfaces on which the code depends. This is a study-specific working definition rather than a universal definition of hallucination. Code hallucinations have been characterised in the literature as affecting the correctness, maintainability, and security of generated software [Gao et al., 2025]. Some of these errors are not detectable by inspecting syntax alone: execution-based verification has been used to expose code hallucinations that pass static syntax checks [Tian et al., 2025]. This observation is relevant to the present study because a dependency reference can be syntactically well formed, for example, a correctly written import statement or a valid `package.json` entry, while still naming a package that cannot be resolved.

External dependencies represent a particular reliability concern within generated code. Modern software makes extensive use of reusable third-party components distributed through public package registries, and the security of these open-source software supply chains has become an established research area. The literature has, for example, systematised attacks on open-source software supply chains [Ladisa et al., 2023], examined supply-chain attacks on package managers for interpreted languages [Duan et al., 2020], and set out research directions for software supply-chain security [Williams et al., 2025]. Within this context, a dependency reference differs from an ordinary logic error. An incorrect loop condition affects the behaviour of the code in which it appears, whereas a dependency reference points outside the generated code to a component that must be retrieved from a registry. The validity of that reference therefore depends not only on the model's output but also on the state of the external registry at the time the reference is acted upon.

Package hallucination concerns the case in which an LLM recommends or imports a package that does not exist as a legitimate package in the target ecosystem. The literature has identified this as a distinct concern arising from the convergence of non-deterministic LLM package recommendations and public package registries [Spracklen et al., 2025; Al-Zofi, 2025]. It is important to distinguish package hallucination from established dependency-based attack techniques with which it is sometimes discussed. Typosquatting exploits misspelled package identifiers, and dependency confusion manipulates the resolution of package names between private and public registries [Al-Zofi, 2025]. The literature further describes *slopsquatting* as the malicious registration of AI-hallucinated dependency names on public package managers [Al-Zofi, 2025]. These concepts are related to package hallucination but are not equivalent to it: a hallucinated package name is a property of a model's output, whereas typosquatting, dependency confusion, and slopsquatting describe adversarial actions performed on a registry or build configuration.

This distinction determines how the supply-chain relevance of package hallucination should be understood. A reference to a nonexistent or otherwise invalid package does not, in itself, constitute an attack or a compromise. It may become a security concern if it is acted upon, for instance, if a developer or automated process attempts to install the named package and a third party has, in the meantime, published a package under that name. Whether such a sequence occurs depends on factors outside the generated response, including developer behaviour, tooling, and registry activity. The present study therefore treats package hallucination as a reliability defect with potential supply-chain consequences, not as evidence of exploitation. It did not register, reserve, publish, install, or execute any package, and it did not simulate an attack.

Registry lookup and static dependency analysis have been described in the literature as approaches for examining package references before installation [Al-Zofi, 2025; Duan et al., 2020; Ohm and Stuke, 2023]. In the present study, read-only registry evidence was used as one input to classification rather than as a self-explanatory outcome: a name may fail to resolve because it was never published, because a real package was cited under an incorrect scope or a slightly different name, because a package was later removed or deprecated, or because the reference denotes a local module rather than a public dependency. Treating every registry absence as a hallucination would therefore conflate distinct failure mechanisms. This methodological consideration shaped the classification approach described in Chapter 3.

Although package-hallucination literature considers more than one package ecosystem, the empirical work reported in this dissertation is confined to Node.js and the npm registry. Restricting the experiment to one ecosystem was a design choice to hold the registry context constant and support detailed analysis of npm dependency references within the study boundary. Other ecosystems are outside the empirical scope. Within this setting, the study examined explicit, direct npm dependency references, such as import and `require` statements, `npm install` commands, and `package.json` dependency entries, in responses generated for standardised Node.js coding tasks. Transitive dependencies, the behaviour of installed packages, and the execution of generated code were not examined.

## 1.3 Research Problem

LLM-generated Node.js solutions may specify the npm packages on which they depend, and a developer who adopts such a solution may use those references when constructing, installing, or running it. When a referenced package cannot be resolved in the npm registry, the solution is, at a minimum, unreliable as supplied. The concern addressed by this dissertation is how often, and in what forms, such dependency-reference failures arise in LLM-generated Node.js responses, and in particular how many of them represent genuinely invented package names rather than other kinds of dependency error.

The research problem involves two related but distinct constructs that must be measured separately. The first is the *confirmed npm package-name hallucination*: an external npm package reference presented by the model as a usable dependency for which conservative validation and adjudication establish that the name is not a legitimate package, after alternative explanations have been ruled out. Confirmation requires more than an npm `404` or `not_found` response; namespace confusion, package-name confusion, legacy or removed status, self/local reference, and other relevant alternative explanations must be addressed under the classification procedure. Where the available evidence does not resolve the classification, the case remains unresolved and is not counted as a confirmed hallucination. The second is the broader class of *exact-name npm dependency-resolution failures*: references that would not resolve as written, but for which the evidence does not establish an invented package. Such failures include namespace confusion, in which a real package is cited under an incorrect scope; package-name confusion, in which a name closely resembles, but does not match, a real package; references to legacy or removed packages; and self-referential or local package names that denote the project being generated rather than an external dependency. Although each of these outcomes may cause an installation or resolution failure, they reflect different underlying errors and carry different practical implications. Collapsing them into a single "hallucination" category would overstate the frequency of invented packages and obscure the diversity of dependency-reliability failures.

The central measurement difficulty is that registry evidence does not by itself determine the research classification. An npm `404` or `not_found` response indicates that a name could not be retrieved at the time of validation; it does not establish why. Registry evidence must therefore be interpreted through a defined classification and adjudication procedure before a reference can be counted as a confirmed hallucination, and references that remain unresolved must be reported as such rather than assigned to either category. The study accordingly reports confirmed package-name hallucination through two primary measures, the Package Hallucination Rate (PHR) and the Sample Hallucination Rate (SHR), and reports exact-name dependency-resolution failure separately through two secondary and exploratory measures, the Dependency Failure Rate (DFR) and the Response Dependency Failure Rate (RDFR). The latter two measures describe dependency-resolution reliability; they are not hallucination rates, and they do not capture every form of dependency unreliability, such as incorrect versions or misused package interfaces. The precise definitions, units, and denominators of these measures are given in Chapter 3.

A controlled empirical assessment is needed because the frequency and form of these failures cannot be inferred from isolated examples or from registry lookups alone. Model outputs are non-deterministic, so a single generation per task provides limited evidence about the stability of a model's dependency recommendations. The inclusion of specialised technical task domains is an analysis and design choice that permits outcomes to be grouped by task category; it does not presume that any category will produce a particular outcome. An assessment of the problem therefore requires a fixed set of standardised tasks, three planned separate generations under the same frozen task and model conditions, with each request made without previous conversational context and with the seed not controlled, a controlled collection protocol, and a consistent procedure for extracting, validating, and classifying package references. The implemented study used standardised Node.js coding tasks across functional categories, frozen model conditions, and three planned separate generations. Within this design, outcomes can be described, and, where the data permit, compared, across model conditions and task categories.

Finally, the practical significance of a confirmed hallucination is not uniform. Depending on the role of the named package, a confirmed finding may cause little more than a setup or installation failure, or it may affect a central functional, reliability, or security requirement of the requested implementation; some findings are also more readily revealed by normal development controls than others. The research problem therefore extends beyond prevalence to the assessment of practical risk for eligible confirmed findings, using a transparent rule-based framework applied after classification. This assessment is intended as an ordinal prioritisation of confirmed findings within the evaluated conditions; it does not estimate the probability of exploitation, the likelihood that a developer will install a package, or any real-world loss.

## 1.4 Research Gap

Package hallucination has received attention in the recent literature. Spracklen et al. (2025) analysed package hallucinations produced by code-generating LLMs, Zhao et al. (2025) developed an approach for testing LLMs for package hallucinations, and Al-Zofi (2025) reviewed package hallucination and slopsquatting from a software supply-chain perspective. Broader work on software supply-chain security provides the context in which dependency-related risks are understood [Ladisa et al., 2023; Williams et al., 2025]. The research gap addressed by this dissertation is therefore not the absence of prior work on the topic. It concerns the need for a bounded, reproducible assessment that connects each reported dependency outcome to preserved evidence under clearly defined experimental conditions, and that separates confirmed package-name hallucination from other exact-name dependency failures.

The first element of this gap is definitional. As discussed in Section 1.3, whether a registry absence is counted as a hallucination depends on how the underlying evidence is interpreted. An assessment that equates registry non-existence with hallucination measures something different from one that adjudicates namespace confusion, package-name confusion, legacy or removed packages, self-referential names, and unresolved cases separately. Prevalence figures are interpretable only in relation to such definitional choices. The present study therefore adopts a conservative primary construct, confirmed package-name hallucination, and reports the broader class of exact-name dependency-resolution failures through separate secondary and exploratory measures, so that the two are neither conflated nor lost.

The second element concerns traceability and repeatability. Because LLM outputs are non-deterministic and the models and serving conditions available for study may change over time, the value of an empirical assessment depends on the degree to which its inputs, conditions, and outputs are fixed and recorded. The implemented study used a frozen set of standardised Node.js/npm coding tasks, frozen model conditions and a controlled collection protocol, with three planned separate fresh requests per task-condition combination, each made without previous conversational context and with the seed not controlled. It retained response evidence and linked the derived package references, registry evidence, classifications, and metrics at a high level. This evidence chain permits reported outcomes to be traced from the generated response, through the extracted and normalised package reference and the read-only npm registry evidence, to the adjudicated classification and the metric in which it is counted.

The third element concerns the relationship between measurement and practical consequence. Prevalence alone does not indicate which confirmed findings merit the greatest attention. The study therefore combines prevalence measurement with grouped comparisons across model conditions and functional task categories, where the data make such comparisons estimable, and with a rule-based practical-risk assessment of eligible confirmed findings. The risk assessment is transparent and deterministic rather than predictive, and it is applied only after classification, so that unconfirmed or unresolved references are not scored as though they were established hallucinations.

The dissertation does not claim that any of these elements, standardised tasks, repeated generation, explicit package extraction, registry evidence, adjudication, or rule-based risk assessment, is individually new. The rationale for the present study lies instead in their integration within a single, implementation-facing assessment of Node.js/npm dependency references under defined experimental conditions. This integration is intended to produce findings whose scope, definitions, and evidential basis are explicit, so that they can be interpreted, audited, and compared with other work on appropriate terms. The findings of the study are accordingly bounded by the evaluated tasks, model conditions and controlled collection protocol, and registry state at the time of validation, and they are not presented as estimates for LLM-generated code in general.

## 1.5 Research Aim

The aim of this study is:

“To assess confirmed npm package-name hallucinations and secondary exact-name dependency-reference reliability failures in LLM-generated Node.js coding responses across the evaluated experimental conditions and functional task categories, and to assess eligible confirmed findings using the implemented practical-risk framework.”

---

## 1.6 Research Objectives

To achieve this aim, the study is guided by the following objectives:

1. **O1.** Measure the prevalence of confirmed npm package-name hallucinations in eligible LLM-generated Node.js coding responses using PHR and SHR.
2. **O2.** Characterize secondary exact-name npm dependency-resolution failures using the implemented DFR/RDFR framework and adjudication taxonomy.
3. **O3.** Examine how package-hallucination and dependency-reliability outcomes vary across the evaluated model conditions and functional task categories, using descriptive and, where estimable, statistical comparisons.
4. **O4.** Assess the practical risk of eligible confirmed package-hallucination findings using the implemented Impact × Detectability risk model.

---

## 1.7 Research Questions

The following research questions operationalise the objectives:

1. **RQ1.** What is the prevalence of confirmed npm package-name hallucinations in LLM-generated Node.js coding responses under the evaluated experimental conditions?
2. **RQ2.** What secondary exact-name npm dependency-resolution failure patterns are observed in the generated responses under the implemented adjudication framework?
3. **RQ3.** How do confirmed package-name hallucination and secondary dependency-reliability outcomes vary across the evaluated model conditions and functional task categories?
4. **RQ4.** What practical risk levels are assigned to eligible confirmed package-hallucination findings under the implemented risk-assessment framework?

## 1.8 Scope and Delimitations

The empirical scope of this dissertation is deliberately narrower than the wording of its title. It concerns LLM-generated Node.js coding responses and the npm package ecosystem, rather than all forms of fake APIs and libraries in AI-generated code. The unit of substantive interest is an explicit, direct dependency or package reference, including references expressed through import or `require` statements, installation instructions, or `package.json` dependency entries. The study uses 30 standardised coding tasks distributed across six functional task categories. The tasks were designated as medium difficulty during pre-freeze task design using a qualitative study rubric; the designation was not externally calibrated and was not used as an analytical variable.

The final frozen study, v2.7.0, comprises three frozen model conditions, identified as M1 (`cohere/north-mini-code:free`), M3 (`openai/gpt-oss-120b`), and M4 (`nvidia/nemotron-3-ultra-550b-a55b:free`), and three planned repetitions for each task-condition combination, giving 270 planned observations. Of these, 140 observations are assigned to API collection and 130 to manual collection; this interface allocation is not balanced across model conditions, and its implications are addressed in Chapter 3. One originally planned condition, M2, was removed after partial collection and before final analysis because its intended collection protocol could not be completed consistently. Previously collected M2 evidence has been preserved but is excluded from final-study analysis, and the retained conditions keep their original identifiers. Chapter 3 reports this decision in full. Responses are obtained under a controlled collection protocol and are processed through explicit package-reference extraction and normalisation, read-only npm registry validation, and conservative classification and adjudication. Confirmed package-name hallucination is assessed through the primary PHR and SHR measures. Exact-name dependency-resolution failure is considered separately through the secondary and exploratory DFR and RDFR measures; these are not hallucination rates. The design also permits grouped comparisons by model condition and functional task category where estimable. Under the implemented practical-risk framework, assessment is limited to eligible confirmed package-hallucination findings.

Several boundaries follow from this scope. Java, Maven, and PyPI are not experimental ecosystems in this dissertation. General API hallucination that is not represented by the implemented package/dependency construct is also outside the empirical analysis. The study does not include developer surveys, human participants, developer-expertise variables, autonomous-agent evaluation, autocomplete-versus-agent comparisons, or verification mediators. It does not involve active package registration, slopsquatting exploitation, package installation, execution of generated dependencies, dynamic malware analysis, or transitive-dependency analysis. It also does not conduct predictive machine-learning modelling, 70/30 train/test modelling, Cohen's Kappa analysis, expert validation, mitigation-system testing, or temporal holdout validation. Such topics may remain relevant as literature context or as directions for future work, but they are not claims about the empirical work performed in this dissertation.

## 1.9 Research Contributions

The study's methodological contribution is a bounded Node.js/npm evidence process that separates explicit package-reference extraction and normalisation, read-only registry validation, and conservative classification and adjudication. It distinguishes confirmed package-name hallucination from broader exact-name dependency-resolution failures and retains the primary PHR/SHR measures separately from the secondary and exploratory DFR/RDFR measures. This structure supports a traceable relationship between a generated response, its package-reference evidence, the resulting classification, and any metric or risk assessment derived from that classification.

Its experimental and dataset contribution is the controlled task and response design used for this assessment: standardised Node.js/npm tasks across functional categories, repeated frozen model conditions, and preserved response and provenance evidence. This contribution concerns the design and evidence basis of the study; it does not imply that collection completion or final analysis has already been achieved.

The study also provides a practical, rule-based Impact × Detectability assessment for eligible confirmed findings. This assessment is an ordinal prioritisation mechanism applied after classification. It is not a predictive model and does not estimate package safety, maliciousness, installation probability, exploitation probability, or real-world loss.

The empirical contribution remains pending final analysis of the frozen v2.7.0 study. The completed analysis is intended to provide evidence on prevalence, secondary failure patterns, grouped outcomes, and practical-risk results within the evaluated conditions. No prevalence estimate, model or category ranking, statistical conclusion, risk distribution, or final number of hallucinations is asserted in this chapter.
