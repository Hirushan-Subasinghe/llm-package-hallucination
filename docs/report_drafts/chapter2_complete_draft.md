# Chapter 2 — Literature Review

## 2.1 Chapter Introduction

This chapter reviews the literature that provides the conceptual and empirical context for the dissertation. Its purpose is to establish how the problem examined in later chapters—the reliability of npm package references in LLM-generated Node.js code—relates to existing research on LLM-assisted software development, code hallucination, software dependency ecosystems, and software supply-chain security. The review does not introduce empirical findings from the present study. Rather, it sets out the concepts, distinctions, and methodological considerations on which the study's design and interpretation depend, and it identifies the respects in which the existing literature informs, and bounds, what an empirical assessment of generated dependency references can reasonably claim.

The review proceeds from the general to the specific. It begins with the use of Large Language Models (LLMs) for code generation and with the reliability limitations that the literature associates with generated code, including the phenomenon described as code hallucination (Section 2.2). It then turns to the external environment on which generated code frequently depends: reusable third-party packages, the package managers that retrieve them, and the public registries through which they are distributed (Section 2.3). Because this environment is also a recognised surface for software supply-chain attacks, Section 2.4 examines threats that operate through package names, such as typosquatting and dependency confusion, and distinguishes them from errors in which no adversary is involved. The subsequent sections narrow the focus further to package hallucination in LLM-generated code and to slopsquatting as a downstream security concern (Section 2.5), before considering validation and classification approaches, reliability and risk, the dimensions along which prior studies differ, and the resulting research gap.

Two boundaries apply throughout. First, the literature reviewed here spans several programming languages and package ecosystems, and some of the most relevant studies were conducted outside the npm ecosystem. Such work is treated as context: the empirical study reported in this dissertation was confined to Node.js and the npm registry, and cross-ecosystem literature is not presented as evidence about ecosystems that the study did not examine. Second, the security literature discussed in this chapter describes attacks and attack scenarios that the present study did not perform, simulate, or observe. These concepts are reviewed because they clarify why unreliable dependency references matter and how they should be distinguished from one another, not because the dissertation evaluated them experimentally. Within these boundaries, the chapter aims to provide a bounded synthesis of the literature rather than an exhaustive survey of every related field.

## 2.2 Large Language Models in Software Development

### 2.2.1 Code generation and reliability limitations

LLMs are now widely discussed in software-engineering research as tools that can generate source code, complete partially written programs, and propose implementations from natural-language descriptions of a task. Hallucinations in LLM-generated code have become the subject of a dedicated systematic literature review [Gao et al., 2025], alongside broader systematic reviews of hallucination in LLMs generally [Woesle et al., 2025]. The existence of such reviews indicates that the reliability of generated code is treated as an established research concern. It also suggests that code-oriented hallucination may be understood as a domain-specific manifestation of a wider phenomenon, while retaining characteristics that are particular to software, such as the requirement that generated code compile, execute, and interact correctly with external libraries and interfaces.

The studies reviewed here do not characterise generated code as uniformly unreliable. Their emphasis falls instead on the observation that the plausibility of generated code is not a sufficient indicator of its correctness. Tian et al. (2025) note that code produced by LLMs can be syntactically correct and superficially plausible while nevertheless failing to execute or to satisfy the requirements of the task, and they propose execution-based verification in response. Liu et al. (2026) similarly frame hallucination as a concern that extends beyond functional correctness, developing an empirical categorisation of hallucinations in LLM-generated code. Taken together, these studies suggest that the evaluation of generated code cannot rely solely on whether the output appears well formed, and that the kind of check applied determines which kinds of error can be observed.

A related theme concerns the structure of software itself. Code differs from ordinary prose in that it must conform to formal syntax, reference identifiers defined elsewhere, and operate within the constraints of a particular language, runtime, and set of libraries. Related work has examined the implications of not treating code as natural language for repository-level code generation [Le-Anh et al., 2026], and other work has examined the identification and mitigation of API misuse by LLMs [Zhuo et al., 2025]. These strands of research are noted here as context. Their relevance to the present study lies in a more general observation: generated code frequently depends on entities outside the immediate text of the response—files, interfaces, and libraries—whose existence and behaviour cannot be confirmed from the generated output alone.

The probabilistic character of generation adds a further consideration. Spracklen et al. (2025), in their analysis of package hallucinations by code-generating LLMs, state that probabilistic generation contributes to diversity in model outputs, and their study examined both the repetition of outputs and the effect of varying the sampling temperature. The broader implication for empirical work is methodological: a single generated response to a task provides limited evidence about how a model behaves on that task, because a repeated request under the same conditions may yield a different response. Studies that seek to characterise the reliability of generated code therefore need to consider repetition, fixed generation conditions, and the preservation of the specific outputs from which conclusions are drawn. This consideration is revisited in Section 2.8, where the dimensions along which prior empirical studies differ are compared.

Reliability concerns also bear on debugging and verification. Where generated code contains errors that are not evident from its surface form, the burden of detecting those errors shifts towards review, testing, and other forms of validation external to the model. Related work has examined approaches intended to make LLM-based coding more reliable, trustworthy, and explainable for production systems [Dubey and Madisetti, 2026]. The execution-based and review literature discussed above [Tian et al., 2025; Gao et al., 2025] indicates that validation of generated code is an explicit activity with its own design choices, rather than a property that can be assumed from the generating model. That point frames the treatment of hallucination in the following subsection.

### 2.2.2 Code hallucination as a software-engineering concern

Chapter 1 adopted a study-specific working definition of hallucination as generated software output presented as valid but not supported by the relevant external reality. The reviewed studies do not converge on a single universal definition of *code hallucination*. Gao et al. (2025) review the characterisation of code hallucinations in LLMs, together with proposed causes, detection and evaluation approaches, mitigation methods, and open challenges, and their review illustrates that the concept is applied to a range of errors rather than to one precisely bounded phenomenon. Liu et al. (2026) contribute an empirical categorisation of hallucinations in generated code, and related work has examined hallucinations in LLM-generated code more generally [Agarwal et al., 2024] as well as security-related code hallucinations specifically [Daoud, 2026]. The general literature on LLM hallucination provides a wider conceptual backdrop [Woesle et al., 2025], but it does not by itself define what counts as a hallucination in code or in a dependency reference.

Two points recur across the studies whose full findings are discussed here [Gao et al., 2025; Liu et al., 2026; Tian et al., 2025]. The first is that hallucination in code is a reliability concern: it affects whether a generated solution can be used as supplied. The second is that hallucinated content may not be evident from surface inspection, because generated code can be syntactically correct and plausible while failing to execute or to satisfy the task requirements [Tian et al., 2025]. The sources differ, however, in emphasis and in the validation method through which hallucination is operationalised. A systematic review such as that of Gao et al. (2025) organises the field conceptually; an empirical categorisation such as that of Liu et al. (2026) derives categories from observed generated code; and an execution-based approach such as that of Tian et al. (2025) identifies hallucination through the behaviour of code when it is run. These differences are not merely presentational. The method used to detect hallucination determines which errors become visible: an execution-based check can reveal behavioural failures that a syntactic check would miss, whereas an error that consists of referring to an external entity that does not exist may require evidence from outside the code altogether.

This last category is of particular relevance to the present dissertation. A generated program may be internally consistent and syntactically well formed while referring to a library, interface, or package whose existence depends on an external source of truth. The validity of such a reference cannot be established from the generated text alone; it requires comparison with the relevant documentation, index, or registry. Research on library hallucinations in LLM-generated code has examined this class of error in the setting of developer queries [Twist et al., 2026], and research on package hallucination has examined the case in which the external entity is a package distributed through a public registry [Spracklen et al., 2025]. These studies are considered in detail in Section 2.5. For the present discussion, their significance is conceptual: they show that one form of code hallucination is located not in the logic of a program but in its dependencies.

The literature on code hallucination therefore supplies three considerations that carry forward into the remainder of this chapter. First, because no single definition is universally adopted, any empirical study must state its own operational definition and the evidence required to apply it. Second, the choice of validation method shapes what can be measured, so that results obtained under one method are not straightforwardly comparable with results obtained under another. Third, a subset of code hallucinations concerns references to external components, whose assessment depends on the state of an external system. The next section examines that external system—software dependency ecosystems and package registries—before Section 2.4 considers the security threats that operate through package names.

## 2.3 Software Dependency Ecosystems and Package Registries

### 2.3.1 Dependencies and the software supply-chain context

Contemporary software development relies extensively on reusable components that are developed and maintained by parties other than the developer who uses them. Rather than implementing every capability directly, developers commonly incorporate open-source libraries and frameworks that provide functionality such as network communication, data parsing, authentication, or testing. This practice supports productivity and reuse, but it also means that a software product depends on code that its developers did not write and may not have reviewed. The software supply-chain security literature treats this relationship as a security-relevant dependency in its own right: open-source dependencies and components constitute a context through which attacks on downstream software can be attempted [Ladisa et al., 2023; Williams et al., 2025].

The literature approaches this context at different levels of abstraction. Ladisa et al. (2023) systematise attacks on open-source software supply chains in the form of a taxonomy. Williams et al. (2025) set out research directions in software supply-chain security and identify dependencies as one of the vectors through which such attacks can occur. Duan et al. (2020) take a more empirical, ecosystem-focused perspective, measuring supply-chain attacks on the package managers of interpreted languages. Although these works differ in method—taxonomic synthesis, research agenda, and empirical measurement respectively—they agree that the mechanisms by which third-party components are obtained are a meaningful object of security analysis, and not merely a matter of development convenience. Related work has also systematised the practical detection of software supply-chain attacks [Ohm and Stuke, 2023], and a research agenda has applied the supply-chain perspective to LLMs themselves [Wang et al., 2025].

For the purposes of this dissertation, the significance of the supply-chain literature is twofold. First, it indicates that a dependency is not a neutral detail of an implementation: the choice of which external component to rely upon has consequences for the reliability and security of the resulting software. Second, it indicates that the consequences of a dependency choice depend on the surrounding context, including the registry from which the component is retrieved, the controls applied before it is installed, and the behaviour of other actors in the ecosystem [Ladisa et al., 2023; Williams et al., 2025]. This contextual dependence is important because it cautions against treating any single dependency-related observation as evidence of compromise. A dependency reference is an instruction to obtain a component; whether acting on that instruction leads to a reliability failure, a security incident, or neither depends on conditions beyond the reference itself.

The supply-chain literature is also broader than the question of whether a named dependency exists. The taxonomic and research-agenda work cited above addresses attacks on open-source software supply chains in general, rather than package names specifically. The present dissertation does not examine these wider threats. It draws on the supply-chain literature for a narrower purpose: to explain why the validity of a package name in generated code is relevant beyond the immediate correctness of the program, and to situate package-name errors within a recognised field of security research without implying that such errors are themselves attacks.

### 2.3.2 Package managers, registries, and npm as one ecosystem

Package managers are the tools through which dependencies are declared, resolved, and retrieved. In a typical workflow, a developer or build process specifies the name of a required package—and, optionally, a version—and the package manager resolves that name against one or more registries, downloads the corresponding artefact, and makes it available to the project. The package name is therefore the key through which the developer's intention is connected to a specific component published by a specific party. This arrangement has an important consequence: the meaning of a dependency declaration is not contained within the declaration itself but is determined by the state of the registry at the time the name is resolved. A name that resolves to a legitimate, maintained package at one time may resolve differently, or not at all, at another.

Public registries serve large communities of publishers and consumers, and the security literature has examined them as points at which malicious or unwanted components can enter the software supply chain. Duan et al. (2020) analysed supply-chain attacks on package managers for interpreted languages, examining how registries can be abused to distribute malicious packages, and developed an analysis approach that combined metadata, static, and dynamic analysis to identify such packages. Their work illustrates that registry-level analysis can draw on several forms of evidence, and that the presence of a package in a registry does not in itself establish that the package is benign. Spracklen et al. (2025) make a related point in the context of package hallucination: a package name that exists in a registry is not thereby shown to be safe, because existence and trustworthiness are different properties. Conversely, as Section 2.4 discusses, a name that is absent from a registry may be absent for more than one reason.

Registry evidence also plays a central role in empirical research on package hallucination, because it provides an external reference against which generated package names can be compared. Spracklen et al. (2025) cross-referenced package names produced by code-generating LLMs against registry information in their evaluation of both Python and JavaScript code generation. Such work indicates that registry comparison is a recognised means of gathering evidence about generated dependency references. It does not, however, establish that registry comparison alone is sufficient to classify every reference, a question that Section 2.6 examines in relation to validation and classification approaches.

Within this broader landscape, npm is the package ecosystem associated with the Node.js runtime and is one of several language-specific ecosystems examined in the literature. It is the ecosystem to which the empirical work of this dissertation was confined. Because npm package names may be scoped, imports may refer to subpaths within a package, and generated code may also refer to Node.js built-in modules or local files, the text of a generated import or installation instruction cannot simply be equated with an npm package name. The specific normalisation rules applied in this dissertation are described in Chapter 3.

The selection of npm for the empirical study should not be read as a claim that npm is uniquely vulnerable, or that its design explains outcomes differently from other ecosystems. Cross-ecosystem literature—including package-hallucination research spanning Python and JavaScript [Spracklen et al., 2025] and measurement of supply-chain attacks across interpreted-language package managers [Duan et al., 2020]—provides useful context for understanding registries in general. However, the literature reviewed in this chapter does not provide evidence on which to base causal claims about how particular registry naming or publication policies determine the frequency of package-name errors. Such claims are therefore not made in this chapter. The present dissertation treats npm as a single, well-defined registry context within which package references can be examined consistently, and it leaves comparisons across ecosystems outside its empirical scope.

The dependence of a package reference on external registry state has a methodological implication that connects this section to the next. Because a dependency declaration is resolved by name, errors in the name—whether accidental, adversarially induced, or generated by a model—are consequential. They may cause installation to fail, may cause a different component from the one intended to be retrieved, or, in some circumstances, may create an opportunity for a third party to supply a component under the erroneous name. The security literature has examined several of these possibilities as distinct threats that operate through package names. Section 2.4 reviews those threats and distinguishes them from the phenomenon of package hallucination.

## 2.4 Software Supply-Chain Threats Related to Package Naming

Because package managers resolve dependencies by name, package names constitute an attack surface within the software supply chain. Several attack techniques discussed in the literature exploit the gap between the package a developer intends to use and the package that a name actually resolves to. This section reviews two techniques that the reviewed literature distinguishes explicitly, typosquatting and dependency confusion, and then considers the broader set of package-manager threats and the distinctions between accidental dependency errors, adversarial package naming, and hallucinated package names. The aim is not to survey supply-chain attacks comprehensively, but to establish conceptual boundaries that prevent package hallucination from being conflated with established attack techniques.

### 2.4.1 Typosquatting

Typosquatting is a package-naming attack in which an adversary publishes a package under a name that closely resembles the name of a legitimate package, in the expectation that some users will install the malicious package by mistake. Al-Zofi (2025) characterises typosquatting as a similar-name attack rooted in human error, in which developers mistype or misread the name of the package they intend to install. Spracklen et al. (2025) likewise treat attacks based on similar names as a form of package confusion, and they discuss such attacks separately from the case in which a generated package name is fictitious. The defining features of typosquatting are therefore intentional adversarial registration and resemblance to an existing legitimate name: the attack depends on the legitimate package being known and on a plausible error in reproducing its name.

This characterisation has two implications for the analysis of generated dependency references. First, typosquatting presupposes a legitimate target. A generated package name that closely resembles a real package may reflect an error related to that real package—for example, an incorrect spelling or an inaccurate recollection of its name—rather than the invention of an entirely new package. Such cases may be better understood as name confusion than as fabrication, and they are relevant to classification because they have a different relationship to the ecosystem from a name with no legitimate counterpart. Second, resemblance alone does not establish that an attack has taken place. A mistyped or confused name in generated code is an error in the output; it acquires security significance only if an adversary has registered the resembling name and a user or automated process retrieves the resulting package. The literature on typosquatting therefore informs how name similarity should be interpreted, but it does not justify treating every similar-looking name as malicious.

### 2.4.2 Dependency confusion

Dependency confusion operates through package resolution rather than through visual resemblance. Al-Zofi (2025) describes it as an attack in which an adversary registers, on a public registry, a package bearing the name of a package that an organisation uses internally, so that package resolution selects the public version rather than the intended internal one. The attack exploits the way in which resolution behaviour selects between package sources or namespaces, and it can succeed even when the dependency name is written exactly as intended, because the vulnerability lies in which source the name is resolved against.

Dependency confusion is thus conceptually distinct both from typosquatting and from package hallucination. It does not depend on a mistyped name, and it does not depend on a model generating an invented name; it depends on the existence of a legitimate internal name and on resolution behaviour that can be influenced by public registration. Direct support for this definition within the reviewed literature comes from Al-Zofi (2025), and the concept is included here to clarify the boundaries of package-naming threats rather than as a phenomenon examined empirically in this dissertation. Its relevance to the analysis of generated code is limited but instructive. A generated reference to a package name that is not found on a public registry does not, in itself, indicate dependency confusion; it may also reflect a name that was never published, a name associated with a private or local context, or an error in the name. Treating such observations as evidence of dependency confusion would attribute an adversarial mechanism to what may be a non-adversarial error.

### 2.4.3 Related package-manager threats and the distinction from package hallucination

Typosquatting and dependency confusion are two instances of a wider class of threats that exploit package managers and registries. Duan et al. (2020) measured supply-chain attacks on package managers for interpreted languages, examining the distribution of malicious packages through registries and analysing such packages using combined metadata, static, and dynamic evidence. The taxonomy of Ladisa et al. (2023) and the research agenda of Williams et al. (2025) place attacks involving dependencies within a broader landscape of threats to open-source software supply chains. Because these works address software supply-chain attacks at a broader level than package naming, they indicate that the threat landscape extends beyond the naming-based techniques reviewed in Sections 2.4.1 and 2.4.2. They also indicate that the consequences of any particular dependency error depend on context—on which package is retrieved, by whom, under what controls, and with what subsequent behaviour [Ladisa et al., 2023; Williams et al., 2025].

Against this background, it is possible to distinguish three categories that are sometimes discussed together but differ in origin and implication. The first is *accidental dependency error*: a developer or tool, which may include an LLM, cites an intended legitimate package incorrectly—for example, by using an outdated name, the wrong scope, or a misremembered spelling—without any adversary being involved. The second is *adversarial package naming*: an attacker deliberately arranges for a name to resolve to a malicious component, as in typosquatting or dependency confusion. The third is *package hallucination*: Spracklen et al. (2025) use the term for the case in which generated code recommends or references a package that does not exist, and Zhao et al. (2025) similarly describe LLMs recommending non-existent packages. Package hallucination is thus defined by two features—the name originates in model output, and the referenced package does not exist—rather than by the actions of an attacker. The boundary between the first and third categories is not always evident from the name alone, because model output may also contain mis-scoped or misspelled references to real packages; how this boundary was operationalised in the present study is described in Chapter 3.

The literature also describes a downstream scenario that connects package hallucination to adversarial naming. *Slopsquatting* refers to the malicious registration of package names that LLMs hallucinate, so that a user who acts on a hallucinated reference may retrieve a package supplied by an attacker [Al-Zofi, 2025]. Spracklen et al. (2025) present a comparable package-confusion attack scenario in which the adversary registers a hallucinated name and a user subsequently installs the package. In both accounts, the attack depends on conditions additional to the hallucination itself: an adversary must register the name, and a user or automated process must act on the generated reference. A hallucinated package name is therefore not equivalent to an attack or to a compromise; it is a reliability defect that may acquire security significance if those further conditions are met. Slopsquatting is considered in more detail in Section 2.5.

These distinctions have direct consequences for how empirical observations of generated dependency references should be interpreted. An observation that a generated package name does not resolve in a registry is compatible with several explanations: the name may never have been published, it may be a mis-scoped or misspelled form of a real package, it may refer to a package that existed previously, or it may denote a local module rather than an external dependency. Only the first of these corresponds straightforwardly to package hallucination as defined in the literature, and none of them, on its own, constitutes an attack. Equally, the fact that a generated name does resolve to a published package does not establish that the package is the one intended or that it is safe [Spracklen et al., 2025]. The naming-threat literature therefore reinforces the need, identified in Section 2.2.2, for explicit operational definitions and for classification procedures that separate distinct failure mechanisms rather than combining them under a single label.

It should be emphasised that the concepts reviewed in this section serve an interpretive function in this dissertation. Section 2.5 turns from these naming threats to the empirical literature on package hallucination itself.

## 2.5 Package Hallucination in LLM-Generated Code

Section 2.4 distinguished package hallucination from adversarial package-naming techniques and accidental dependency error. This section defines package hallucination, synthesises empirical package and library-hallucination research, and considers slopsquatting as a downstream security scenario.

### 2.5.1 Concept and terminology

In the reviewed literature, package hallucination refers to a specific kind of error in generated code: the recommendation of, or reference to, a software package that does not exist. Spracklen et al. (2025) use the term for the case in which code generated by an LLM recommends or references a non-existent package, and Zhao et al. (2025) similarly describe LLMs recommending packages that do not exist. In relation to the wider code-hallucination literature discussed in Section 2.2.2, package hallucination can be understood as a manifestation of code hallucination that is located in a dependency reference rather than in the logic of a program. What distinguishes it from many other forms of code hallucination is the source of truth against which it must be assessed. Whether a loop is correct can, at least in principle, be examined by reasoning about or running the code; assessing the status of a named package requires external authoritative evidence, such as the relevant registry or index.

This dependence on external evidence helps to explain why a hallucinated package reference may not be evident from the generated code. A package name is, syntactically, an ordinary identifier or string. An import statement, a `require` call, an installation command, or a dependency-manifest entry that names a non-existent package can be as well formed as one that names a real package, and the surrounding code may use the imagined package in an internally consistent way. Nothing in the syntax of the reference distinguishes a valid dependency from an invented one. The broader observation of Tian et al. (2025), that generated code can be syntactically correct and plausible while failing to execute or to meet the requirements of the task, therefore applies with particular force to dependency references: the plausibility of a reference is not evidence of its validity. A developer who reviews the code for logical correctness may have no reason to question a dependency name that reads naturally, unless the name is checked against the registry or the attempt to install it fails.

Package hallucination should also be distinguished from the broader category of dependency error. A dependency reference in generated code may be defective in several ways that do not involve an invented package: the name of a real package may be misspelled or mis-scoped, a package may be cited that was previously available but has since been removed or deprecated, a version may be specified that does not exist, or a real package may be invoked through functions or members that it does not provide. Some of these defects correspond to the *accidental dependency error* category of Table 2.1, in which an intended legitimate package can be identified. Others concern the interface of a package rather than its existence. Package hallucination, as defined in the literature cited above, is narrower: it concerns the existence of the referenced package. The distinction matters because the categories differ in their relationship to the registry. A misspelled reference to a real package may point towards an identifiable legitimate target, whereas the literature-level package-hallucination construct concerns the non-existence of the referenced name.

The literature does not, however, use a single construct at a single level of granularity. Twist et al. (2026) examine *library* hallucinations in LLM-generated code, operationalised with reference both to the libraries that generated code imports and to the members of those libraries, and validated against a package index and library documentation. Their construct therefore extends from the existence of a library to the validity of the interfaces used within it, whereas the package-hallucination studies of Spracklen et al. (2025) and Zhao et al. (2025) centre on the packages that models recommend or reference. These are related but not identical objects of measurement. An empirical study must therefore state which construct it measures, at which level of granularity, and with what evidence, rather than assuming that the terms *package hallucination*, *library hallucination*, and *dependency error* are interchangeable. The operational definition adopted in the present study, including the evidence required before a reference is treated as a confirmed package-name hallucination, is set out in Chapter 3; it is a study-specific rule and is not presented here as the literature's definition.

### 2.5.2 Empirical research on package and library hallucination

Package hallucination has been examined empirically in several recent studies, which differ in purpose, design, and operationalisation. Spracklen et al. (2025) conducted a comprehensive analysis of package hallucinations by code-generating LLMs. Their evaluation covered both Python and JavaScript code generation, included commercial and open-source models, and cross-referenced the package names that the models produced against registry information. The study also examined whether hallucinated package names were repeated across generations and how outcomes varied with model settings, including the sampling temperature. Zhao et al. (2025) approached the problem from a testing perspective, presenting HFuzzer as a fuzzing-based approach that generates coding tasks through which LLMs can be tested for package hallucinations. Twist et al. (2026), working in a Python-library setting, grounded their analysis in developer queries, varied the formulation of prompts across several LLMs, extracted the libraries imported by generated code, and validated them against the Python Package Index (PyPI) and library documentation. Among the conditions they varied was the inclusion of time-related phrasing in prompts, which illustrates that the way a request is formulated is itself treated as a factor of interest.

Read together, these studies indicate that package and library hallucination has been treated as a measurable property of LLM-generated code. Spracklen et al. (2025) and Twist et al. (2026) both report hallucinated package or library references under their evaluated conditions, and Zhao et al. (2025) present systematic testing as a means of eliciting such references.

The studies differ, however, in ways that limit direct comparison of their findings. They examine different ecosystems (Python and JavaScript in one case and Python libraries in another); they derive tasks from different sources (prompts constructed for large-scale evaluation, systematically generated test tasks, and developer queries); they measure different units (recommended packages, generated tasks, or imported libraries and their members); and they apply different validation procedures (cross-referencing against registry information, testing, or validation against a package index together with documentation). Twist et al. (2026), for example, normalised library names and excluded validly specified explicit versions in order to avoid over-counting, which is an operational choice that affects what their reported figures represent. Because the construct, unit, and validation rule differ, a hallucination rate reported by one study is not directly comparable with a rate reported by another, and none of these rates can be transferred to a different ecosystem, model set, or task design. For this reason, this review does not reproduce the individual rates reported in these studies; where specific figures are relevant to the comparison of study designs, they are considered in Section 2.8 with their source-specific context.

Repetition is a further dimension on which the literature offers direction but not a general law. Spracklen et al. (2025) state that probabilistic generation contributes to diversity in model outputs, and their study examined the repetition of hallucinated names across generations alongside the effect of temperature. The significance of repetition is twofold. Methodologically, it supports treating repeated independent generation under fixed conditions as a more informative basis for an empirical estimate than a single sample. Substantively, it bears on security interpretation, because a name that is produced once in isolation differs from a name that recurs across generations: a recurring name could be generated again for a different user, which is relevant to the downstream scenario discussed in Section 2.5.3. These observations are findings and design choices of the cited study. They indicate that recurrence is worth examining, but they do not establish how often recurrence will occur under other models, tasks, or ecosystems.

The cross-ecosystem character of this literature also requires care. The empirical studies discussed here include Python and JavaScript settings, and the wider package-manager security literature spans several interpreted-language ecosystems [Duan et al., 2020]. These studies examine package or library hallucination in more than one ecosystem setting, but they do not show that outcomes observed in one ecosystem will hold in another. The present study examined npm dependency references only; this literature is used to define relevant concepts and methodological concerns, not to predict its outcomes.

### 2.5.3 Slopsquatting as downstream security context

The security relevance of package hallucination arises principally through the scenario that the literature describes as *slopsquatting*. Al-Zofi (2025), in a systematic review of package hallucinations and slopsquatting attacks, describes slopsquatting as the malicious registration of package names that LLMs hallucinate. Spracklen et al. (2025) present a comparable package-confusion attack scenario, in which an adversary registers a package under a hallucinated name and a user subsequently installs it. Both accounts locate the attack in actions that follow the hallucination: the model produces a non-existent name, an adversary registers that name on a public registry, and a user or automated process acts on the generated reference by installing the package.

This sequence makes clear why package hallucination is not itself an attack. The hallucination is a property of the model's output and involves no adversary. The attack requires, in addition, that an adversary registers the hallucinated name and that a user or process then acts on the generated reference by installing the package. If the name remains unregistered when it is acted upon, the hallucinated reference remains a reliability defect: an installation attempt would fail to resolve it, or the reference may be corrected before use. The distinction is consistent with Table 2.1, in which package hallucination is characterised as a reliability defect originating in LLM output and slopsquatting as a downstream scenario requiring adversarial registration.

Slopsquatting also illustrates why the state of the registry must be interpreted in relation to time. A name that is absent from a registry when it is checked may be registered subsequently, whether by an adversary or by a legitimate publisher. Conversely, the presence of a package under a name does not establish that the package is the one the generated code intended or that it is safe [Spracklen et al., 2025]. A registry observation is therefore evidence about the state of the registry at the time of validation; it is not evidence about whether a name has been, or will be, exploited. This has a direct bearing on the interpretation of empirical work. A study that identifies hallucinated package names has identified names that could, under the further conditions described above, become the subject of a slopsquatting attempt. It has not thereby observed such an attempt, estimated its likelihood, or established that any user would act on the reference.

Al-Zofi (2025) is a systematic review distributed as a preprint, and its account of slopsquatting synthesises the package-hallucination and supply-chain literatures rather than reporting a new primary experiment. Its principal value for this dissertation is conceptual: it places package hallucination within the vocabulary of software supply-chain security while keeping the hallucination and the attack distinct. Together with the attack scenario described by Spracklen et al. (2025), it supports the position adopted throughout this chapter, namely that package hallucination is best understood as a reliability defect with potential security consequences that depend on subsequent adversarial and user actions.

The literature reviewed in this section establishes what package hallucination is, why it may pass unnoticed, how it has been studied, and how it connects to a recognised supply-chain scenario. It also shows that the empirical identification of a hallucinated package depends on the procedure used to extract, validate, and interpret package references. Section 2.6 therefore turns to the approaches through which generated code and its dependency references have been validated and classified.

## 2.6 Detection, Validation, and Classification Approaches

Because a package reference cannot be validated from the generated text alone, every empirical account of package hallucination rests on a procedure for obtaining and interpreting external evidence. The literature reviewed here uses several such procedures, which differ in what they examine and in what they are able to reveal. This section considers registry and reference-level validation, execution-based and other detection approaches, and the step, often left implicit, from detecting a candidate error to classifying it.

### 2.6.1 Registry and reference-level validation

The most direct means of assessing a generated package reference is to compare it with the registry or index of the relevant ecosystem. Spracklen et al. (2025) cross-referenced the package names produced by code-generating LLMs against registry information, and Twist et al. (2026) extracted the libraries imported by generated Python code and validated them against PyPI and library documentation. Registry-level evidence has also been used in the supply-chain security literature for a different purpose: Duan et al. (2020) combined metadata analysis with static and dynamic analysis to identify malicious packages in the registries of interpreted-language package managers. Across these uses, the registry provides time-bounded external evidence about a dependency reference that the generated code itself cannot supply.

Reference-level validation involves more than a single lookup. Before a name can be compared with a registry, it must be identified in the generated output and reduced to the form under which the registry would record it. The work of Twist et al. (2026) illustrates this step: they normalised library names and excluded validly specified explicit versions in order to avoid over-counting. Such operations are not neutral. What is extracted, how it is normalised, and which references are treated as eligible for validation all determine which names reach the registry comparison and, consequently, what any reported rate represents. In the npm ecosystem, as Section 2.3.2 noted, scoped names, import subpaths, built-in modules, and local files mean that the text of an import cannot simply be equated with a package name. The extraction and normalisation rules applied in the present study are therefore described in Chapter 3 as part of its methodology.

Registry lookup also has intrinsic limits. It can establish whether a name resolved in a registry at a particular time; it cannot, on its own, explain why a name failed to resolve or establish that a name which did resolve is legitimate. A name may be absent because it was never published, because it is a mis-scoped or misspelled form of a real package, because the package was previously published and later removed, or because the reference denotes a local module rather than an external dependency. Conversely, as noted in Section 2.5.3, a name that resolves may correspond to a package other than the one intended, and existence does not establish safety [Spracklen et al., 2025]. Existence checking therefore produces evidence that requires interpretation. It is indispensable as a source of evidence about generated dependency references, but a simple mapping from registry absence to hallucination would combine several distinct failure mechanisms under a single label and could misstate the prevalence of the narrower phenomenon.

### 2.6.2 Execution-based and other detection approaches

A second family of approaches examines how generated code behaves rather than what it names. Tian et al. (2025) proposed execution-based verification of code hallucinations, motivated by the observation that generated code may be syntactically correct and plausible while failing to execute or to satisfy the requirements of its task. Execution can reveal behavioural failures that a reference-level or textual check may not establish, and for this reason it can complement reference-level validation. Testing approaches occupy a related position. Zhao et al. (2025) used generated tasks to test LLMs for package hallucinations, so that the testing procedure serves as a means of eliciting such errors systematically. The systematic review of Gao et al. (2025) treats the detection and evaluation of code hallucinations as a distinct area of research alongside their characterisation and mitigation, which indicates that detection is recognised as a methodological problem in its own right rather than as a by-product of code generation.

Related work has also proposed a hybrid approach to hallucination detection in LLM-generated code [Yang et al., 2026], a fact-checking judge for hallucinations in API migration [Tileria et al., 2026], and work that seeks to uncover weaknesses in automatic code generation by LLMs [Lian et al., 2024]. These works are noted as evidence of the breadth of detection and evaluation research; they are not used here to support claims about the accuracy or comparative performance of particular techniques.

Execution-based validation addresses a different question from the read-only registry evidence used in the present study. The present study neither installed packages nor executed generated code; its methodology and the resulting behavioural limitation are described in Chapter 3.

The approaches reviewed above therefore differ less in quality than in the question they answer. Registry and reference-level validation asks whether a named dependency corresponds to a published package; execution-based validation asks whether generated code behaves as required; testing approaches ask how errors can be elicited systematically; and security-oriented registry analysis, such as that of Duan et al. (2020), asks whether a published package is malicious. Each makes visible a different subset of the errors that generated code may contain. As observed in Section 2.2.2, the validation method shapes what can be measured.

### 2.6.3 From detection to classification

Detection and classification are distinct steps. Detection identifies a candidate problem, for example a generated name that did not resolve in a registry. Classification assigns that candidate a research meaning, for example that it represents an invented package rather than a misspelled reference to a real one, and it requires both evidence and an explicit rule for interpreting that evidence. The supply-chain literature illustrates the gap between the two steps in a different setting. In Duan et al. (2020), automated analysis identified candidate malicious packages and subsequent maintainer confirmation did not confirm every reported candidate as malicious. This was malicious-package research, not package-hallucination research; it illustrates only that an automated signal and a confirmed classification are different kinds of statement.

Classification choices directly affect measured prevalence. Whether mis-scoped and misspelled references to real packages are counted as hallucinations, whether previously published but removed packages are distinguished from names never published, whether references to local modules are excluded, and whether the unit of analysis is the package reference, the response, or the task all change the resulting figure. The studies reviewed in Section 2.5.2 make different choices on several of these dimensions, including their units and validation rules, and Twist et al. (2026) explicitly adjusted their procedure to avoid over-counting. The reviewed studies do not apply a common classification scheme. Reported rates must therefore be read together with the construct and rules that produced them, and the choice of rules is part of the substance of an empirical study rather than a technical detail.

A related issue concerns cases that the available evidence does not resolve. A generated reference may be ambiguous, for example a name that resembles a real package closely enough to suggest confusion but not closely enough to establish it, or a reference whose status as an external dependency rather than a local module is unclear from the response. Assigning such cases to either the hallucinated or the valid category would introduce error in one direction or the other. An evidence-based procedure therefore needs a means of recording that the evidence is insufficient, so that unresolved cases are reported as such rather than silently absorbed into a rate. This is a methodological requirement that follows from the limits of registry evidence described in Section 2.6.1; the specific classification and adjudication categories used in the present study are defined in Chapter 3 and are not presented here as an established scheme from the literature.

Finally, the separation of detection from classification bears on reproducibility and traceability. Because registry state changes over time, a validation result is meaningful only in relation to the time at which it was obtained. Because classification depends on rules, a reported outcome can be audited only if the rule applied to each reference is recorded. And because generation is non-deterministic, a classification can be re-examined only if the generated response from which the reference was extracted is preserved. These considerations do not arise from any single cited study. They follow from the combination of external evidence, interpretive rules, and probabilistic generation that the literature reviewed in Sections 2.5 and 2.6 describes, and they are revisited in Section 2.8 in relation to the comparative dimensions of prior research.

Validation and classification determine which generated references are counted as package hallucinations. They do not, however, determine how much a given hallucination matters in practice. Section 2.7 therefore turns from the measurement of hallucinated references to their practical consequences.

## 2.7 Reliability, Security, and Risk Assessment

The preceding sections established that a hallucinated package reference is a reliability defect whose security significance depends on further conditions. This section considers the practical consequences of such defects in more detail. It first examines the reliability and security consequences of invalid dependency references and the distinction between a reliability failure and an actual compromise, then considers risk-oriented perspectives that bear on how the consequences of individual findings can be differentiated, and finally notes related research on reducing hallucination and on the broader development contexts in which generated references are acted upon.

### 2.7.1 Reliability and security consequences

The most immediate consequence of a hallucinated or otherwise invalid dependency reference is a reliability failure. A generated solution that depends on a package that cannot be retrieved cannot be used as supplied: an installation attempt fails, a build does not complete, or the code fails when it attempts to load the missing module. This is consistent with the more general observation of Tian et al. (2025) that plausible generated code may fail to execute or to fulfil its requirements. Such failures impose costs, including time spent diagnosing the failure, searching for a real package that provides the intended functionality, and adapting code written against an imagined interface. They do not in themselves involve any security compromise. Twist et al. (2026) provide related research on library hallucinations grounded in developer queries. This review does not infer a particular practical consequence from the “risk analysis” framing in that work's title.

The security consequences of invalid dependency references arise from the wider supply-chain context reviewed in Sections 2.3 and 2.4. Dependencies are an established vector for attacks on software supply chains [Ladisa et al., 2023; Williams et al., 2025], and the registries of package managers have been examined as channels through which malicious packages are distributed [Duan et al., 2020]. Within this context, a hallucinated package name acquires security significance through the slopsquatting scenario [Al-Zofi, 2025]: if an adversary registers the name and a user or process installs the resulting package, malicious code may be introduced into the software that depends on it. The consequence of a hallucinated reference is therefore conditional. The same generated name may lead to a failed installation if the name remains unregistered, to the retrieval of an unrelated but benign package if a legitimate publisher later adopts the name, or to the retrieval of a malicious package if an adversary registers it.

This conditionality underpins the distinction between a reliability failure and an actual compromise. A reliability failure is established by the invalidity of the reference. A compromise requires, in addition, adversarial action on the registry and an act of installation or execution, neither of which is implied by the reference itself. Consistent with the supply-chain literature's emphasis on the context in which dependencies are obtained [Ladisa et al., 2023; Williams et al., 2025], the consequences of a given hallucinated reference depend on the state of the registry, the controls applied before installation, and the behaviour of the developers and tools that act on the generated code. An empirical study of hallucinated references can therefore establish a precondition for the slopsquatting scenario; it cannot, without further evidence, establish that the scenario has occurred or estimate how likely it is to occur.

The practical consequence of a hallucinated reference also varies with the role of the referenced package. A hallucinated package that is peripheral to the requested functionality, such as an optional development utility, may be removed or replaced with little effect. A hallucinated package on which the central function of the solution depends, or one intended to provide a security-relevant capability such as authentication or cryptography, has greater consequence: the solution fails at its core, and any substitute, whether chosen by the developer or supplied through the registry under the hallucinated name, is placed in a position of greater trust. This variation is not captured by prevalence figures, which count hallucinated references without distinguishing their roles. It is one reason why measures of how often hallucinations occur and assessments of what they imply are complementary rather than interchangeable.

### 2.7.2 Consequence, detectability, and risk-oriented perspectives

Two considerations that bear on differentiating the practical significance of individual findings can be drawn from the literature reviewed above: the consequence of a finding and the likelihood that it will be noticed before it causes harm. The first follows from the context-dependence of supply-chain consequences discussed above [Ladisa et al., 2023; Williams et al., 2025]. The second follows from the observation that plausible generated code may conceal its defects [Tian et al., 2025] and from the attention that the literature gives to detection as a distinct activity [Gao et al., 2025; Duan et al., 2020]. As a matter of dissertation reasoning, detectability may differ across references and use contexts. A reference that fails immediately on installation may be noticed earlier than one whose status becomes relevant only later in use; likewise, a registered name may remove an immediate resolution-failure signal. These are analytical possibilities that motivate attention to detectability, not measured outcomes reported by the cited studies.

Research on dependency risk more generally has also addressed which dependency problems apply in practice: related work has proposed a methodology for counting dependencies that are actually vulnerable [Pashchenko et al., 2022]. Vulnerable dependencies are a different construct from hallucinated ones, and that work is cited here only as topic-level context. Its relevance is that it treats the question of which dependency problems should be counted, and with what practical meaning, as a methodological issue in its own right, a concern that parallels the distinction drawn in Section 2.6.3 between detecting a candidate error and classifying it.

These considerations motivate the assessment of practical risk alongside prevalence, but the reviewed literature does not provide an established scoring scheme for hallucinated package references. The rule-based practical-risk framework applied to eligible confirmed findings in the present study was defined for this study and is described in Chapter 3. It draws on the considerations of consequence and detectability discussed in this section, but it is not presented as a standard derived from the cited literature. Consistent with the distinction drawn above, that framework is an ordinal means of prioritising confirmed findings. It does not measure the probability of exploitation, the likelihood that a developer will install a package, or any realised loss.

### 2.7.3 Related risk-reduction and development-context research

The literature also contains a body of work concerned with reducing hallucination in generated code, several strands of which address API hallucination rather than package-name hallucination specifically. One strand grounds generation in external knowledge about libraries and their interfaces. Related work has examined code generation for unknown libraries by reading API documentation [Washio and Miyao, 2022], and the mitigation of code LLM hallucinations through API documentation [Jain et al., 2025]. Other work has proposed mitigating API hallucination through knowledge-graph reasoning [Li et al., 2026] and through knowledge injection [Liu et al., 2025b], while a different approach seeks to alleviate code hallucination through pseudocode intermediation [Liu, 2026]. Closer to the dependency setting, related work has proposed defences against role-based prompt injection and dependency hallucination in LLM-powered development [AlSobeh et al., 2025]. Spracklen et al. (2025) and Gao et al. (2025) also discuss mitigation directions, although the approaches they consider differ in method and setting. These works are cited to indicate the existence and variety of risk-reduction research. The present study did not implement or evaluate any mitigation approach, and no claim is made here about the effectiveness of those cited.

A further body of work extends the discussion of risk to the settings in which generated code is increasingly produced and acted upon. AI-assisted software development has itself been framed as a supply-chain attack surface [Yadav et al., 2026], and a survey has addressed systemic security risks in vibe coding and autonomous development workflows [Gandhi, 2026]. Related work has also examined supply-chain poisoning attacks directed at the skill ecosystems of LLM coding agents [Qu et al., 2026] and the mitigation of hallucination and overconfidence in agentic AI coders [Tripathi et al., 2025]. These works are cited as topic-level context only. Autonomous or agentic operation was not a variable in the present study, and no empirical finding about such settings is drawn from these sources.

The literature reviewed in this section therefore supports three conclusions relevant to the dissertation. First, a hallucinated package reference is, in the first instance, a reliability defect, and its security significance is conditional on adversarial registration and on the reference being acted upon. Second, the practical significance of individual findings varies with the role of the referenced package and with how readily the defect is noticed, so that prevalence alone does not describe practical risk. Third, although the literature motivates attention to consequence and detectability, the specific framework used to assess risk in an empirical study must be defined and justified by that study. Section 2.8 turns to the dimensions along which prior empirical studies differ and to the implications of those differences for comparison and reproducibility.

## 2.8 Comparative Dimensions in Prior Research

Sections 2.5 and 2.6 showed that empirical studies of package and library hallucination differ in their constructs, units, and validation procedures, and Section 2.7 showed that the practical significance of a hallucinated reference depends on conditions outside the reference itself. This section draws these observations together by considering four dimensions along which prior research varies: models and generation conditions, tasks and prompts, package ecosystems, and measurement and classification rules. The purpose is not to rank studies or reconcile their reported figures, but to identify what must be known about a study before its findings can be interpreted or set beside those of another. The comparisons discussed here concern prior research only; the comparisons performed in the present study are described in Chapter 3.

### 2.8.1 Models and generation conditions

The first dimension is the set of models evaluated. Spracklen et al. (2025) evaluated commercial and open-source code-generating models, Twist et al. (2026) examined library hallucinations across several LLMs, and Tian et al. (2025) evaluated multiple models using execution-based verification. Because studies select models available at the time for their own purposes, a model-level observation in one study cannot be assumed to hold for a different model, a later version of the same model, or the same model accessed under different conditions. The reviewed literature therefore supports treating model identity as a condition that bounds a finding, rather than as a variable whose effect can be generalised from one study to another.

Model identity is not the only relevant generation condition. Spracklen et al. (2025) state that probabilistic generation contributes to diversity in model outputs, and their study varied sampling temperature and examined recurrence of hallucinated package names across generations. Thus, query settings and the number of generations are part of what a reported outcome describes. A finding obtained under one setting is not necessarily informative about the same model under another; repeated designs can additionally describe variability and recurrence across responses.

A further consideration, which is dissertation reasoning rather than a finding of any cited study, concerns the stability of these conditions. Because the models accessible to researchers, and the conditions under which they are served, may change over time, a finding about a model is most interpretable when the model identity, generation settings, and underlying responses are recorded.

### 2.8.2 Tasks, prompts, and temporal conditions

The second dimension concerns how generated code is elicited. Spracklen et al. (2025) constructed prompts for a large-scale evaluation; Zhao et al. (2025) generated coding tasks systematically through a fuzzing-based approach; and Twist et al. (2026) grounded their analysis in developer queries while varying prompt formulation. These sources sample different regions of the possible-request space, so an outcome observed in one is not necessarily representative of another. Functional domain may also matter because different functionality may call for different dependencies, but the reviewed literature does not establish the direction or size of a domain effect transferable to other task sets.

Prompt formulation is a related but distinct dimension. Among the conditions varied by Twist et al. (2026) was the inclusion of time-related phrasing in prompts, which indicates that the wording of a request, including its reference to time, is treated as a factor that can bear on library-hallucination outcomes in their setting. The present review does not draw a general conclusion about the effect of such phrasing from that study; its relevance here is that prompt wording is itself a condition that should be reported and either controlled or explicitly accounted for when outcomes are compared across models or tasks.

Time also enters the comparison of studies through the state of the registry. Because registry evidence describes a name's status at the time of validation (Sections 2.5.3 and 2.6.1), two studies that validate similar names at different times may obtain different evidence without any difference in model behaviour. A reported outcome is therefore bounded by the period during which registry evidence was collected, as well as by the models and prompts evaluated.

### 2.8.3 Package ecosystems

The third dimension is the ecosystem in which dependency references are assessed. The empirical literature reviewed in this chapter spans several settings. Spracklen et al. (2025) evaluated code generation in both Python and JavaScript, Twist et al. (2026) worked in a Python-library setting validated against PyPI and library documentation, and Duan et al. (2020) measured supply-chain attacks on the package managers of several interpreted languages. Related work has also examined hallucination patterns and mitigation in relation to Rust crates [Zheng et al., 2026]. This breadth shows that dependency-reference errors, and the registry-mediated threats associated with them, have been studied in more than one ecosystem. It does not show that outcomes observed in one ecosystem will be replicated in another.

As a matter of analysis rather than a reported finding of the cited studies, ecosystems may differ in how packages are named and imported and in the relationship between the name used in code and the name under which a package is published. In npm, for example, scoped names, import subpaths, and Node.js built-in modules mean that the text of an import cannot simply be equated with a registry name (Section 2.3.2). An extraction and validation procedure designed for one ecosystem may therefore not transfer directly to another, and a rate reported for one ecosystem reflects its conventions as well as model behaviour. Cross-ecosystem research is accordingly treated in this dissertation as context for concepts and methods, not as evidence about the npm ecosystem in which the present study was conducted.

### 2.8.4 Measurement, validation, and classification

The fourth dimension, and arguably the most consequential for comparison, concerns what is measured and how. The reviewed studies differ in construct: Spracklen et al. (2025) and Zhao et al. (2025) examine packages that models recommend or reference, whereas Twist et al. (2026) examine libraries and the members used within them. They differ in unit: recommended packages, generated tasks, or imported libraries and their members. They differ in validation procedure: cross-referencing against registry information, testing through generated tasks, validation against a package index together with documentation, or, in the wider code-hallucination literature, execution of the generated code [Tian et al., 2025]. At a broader level, the review of Gao et al. (2025) organises code-hallucination research around characterisation, causes, detection and evaluation, and mitigation, while Liu et al. (2026) derive an empirical categorisation of hallucinations in generated code; these works indicate that even the categories into which hallucinations are sorted are products of particular research designs rather than a fixed scheme shared across the field.

Measurement choices extend to the evaluation of detection itself. Related work has examined the prevalence of hallucinations in a different generation direction—the generation of natural-language descriptions from code changes—together with the evaluation of metrics for detecting them [Liu et al., 2025a]. That work concerns generated text about code rather than dependency references in generated code, and its findings are not transferred here. It is noted because it illustrates that the means by which hallucinations are detected is itself treated as an object of evaluation, which reinforces the observation that a reported prevalence depends on the detection method applied.

Classification rules add a further layer of variation. As Section 2.6.3 discussed, the treatment of confused, removed, local, and unresolved references affects the resulting figure, and the reviewed studies do not apply a common classification scheme. The operational rule applied in each study is therefore part of what its reported rate represents.

### 2.8.5 Implications for comparing findings

These dimensions combine. A reported rate of package or library hallucination describes particular models under particular generation settings, responding to particular tasks and prompts, with references assessed in a particular ecosystem, validated by a particular procedure at a particular time, and classified according to particular rules. A difference between the rates reported by two studies may reflect any of these conditions, and the reviewed literature does not provide a means of separating their contributions after the fact. Section 2.5.2 deferred consideration of individual reported figures to this section; the conclusion reached here is that such figures should not be interpreted as directly comparable without accounting for the design conditions that produced them. This review therefore compares study designs rather than study results.

This conclusion does not diminish the value of the reviewed studies. Collectively, they establish that package and library hallucination can be measured under a range of conditions. The reviewed studies do not supply a single shared design frame that would make their figures directly poolable without further harmonisation. The value of new empirical work therefore depends substantially on how explicitly it reports its conditions along these dimensions. Section 2.9 draws on this implication in stating the research gap addressed by this dissertation.

### 2.9.1 What the reviewed literature establishes

The literature reviewed in this chapter establishes several points on which the present study builds. First, hallucination in LLM-generated code is recognised as a reliability concern in its own right. It has been the subject of a dedicated systematic review [Gao et al., 2025], of empirical categorisation [Liu et al., 2026], and of execution-based verification motivated by the observation that plausible generated code may fail to execute or to meet its requirements [Tian et al., 2025]. Second, a subset of such errors concerns dependency references, and package hallucination—the recommendation of, or reference to, a package that does not exist—has been examined empirically under defined conditions [Spracklen et al., 2025; Zhao et al., 2025], alongside related work on library hallucinations at the library and member levels [Twist et al., 2026]. Package hallucination is therefore not an unexplored phenomenon, and this dissertation does not present it as one.

Third, the security relevance of dependency references is well grounded in the software supply-chain literature. Open-source dependencies and package registries have been examined as attack surfaces through taxonomic synthesis [Ladisa et al., 2023], research agendas [Williams et al., 2025], and empirical measurement of attacks on package managers [Duan et al., 2020]. Within this literature, package-naming threats such as typosquatting and dependency confusion are distinguished from one another, and slopsquatting has been described as the malicious registration of names that LLMs hallucinate [Al-Zofi, 2025]. The reviewed accounts consistently locate the attack in actions that follow the hallucination—adversarial registration and a subsequent installation—so that a hallucinated name is a reliability defect with conditional security consequences rather than an attack in itself [Al-Zofi, 2025; Spracklen et al., 2025].

Fourth, the literature contains a range of detection and validation approaches, including registry and reference-level checking, systematic testing, execution-based verification, and security-oriented analysis of published packages. These approaches answer different questions and make different subsets of error visible (Section 2.6). Fifth, as Section 2.8 showed, prior studies differ in the models, generation settings, tasks, prompts, ecosystems, units, and validation rules that they employ.

Taken together, the literature supports the importance of package hallucination as a software-reliability and supply-chain concern, but also shows that findings depend on definitions, validation procedures, evaluated ecosystems, model conditions, and sampling designs. This dependence is the starting point for the research gap addressed here. The gap is not an absence of research on package hallucination, of benchmarks, or of detection methods; each of these exists in the reviewed literature. It concerns, instead, the conditions under which a particular empirical finding about generated dependency references can be interpreted, audited, and related to other work.

### 2.9.2 Literature-supported interpretive limitations

Several limitations that bear on the interpretation of package-hallucination findings follow from the reviewed literature. They are limitations of comparability and interpretation across studies, not deficiencies attributed to any individual study, each of which was designed to answer its own question.

The first is definitional. The reviewed studies measure related but non-identical constructs—non-existent packages, libraries and their members, or behavioural failures of code—at different units of analysis (Sections 2.5.1 and 2.8.4). A figure reported under one construct cannot be read as an estimate of another. The second concerns validation. Registry evidence is informative but time-bounded, and it does not on its own explain why a name failed to resolve; an absent name may reflect invention, confusion with a real package, removal of a previously published package, or a local reference (Sections 2.4.3 and 2.6.1). How a study resolves these possibilities determines what its reported rate represents. The third concerns the step from detection to classification. The reviewed studies do not share a common classification scheme, and the treatment of confused, removed, local, and unresolved references directly affects measured prevalence (Section 2.6.3).

The fourth limitation concerns generation conditions and sampling. As Section 2.8 showed, prior research has treated repetition, generation settings, and prompt formulation as relevant design conditions. Findings are therefore bounded by the models, settings, prompts, and number of generations sampled, and they may not transfer to other conditions. The fifth concerns ecosystem specificity. Although the literature spans several ecosystems, it does not establish that outcomes in one ecosystem predict outcomes in another, and ecosystem conventions affect how references must be extracted and validated (Section 2.8.3). The sixth concerns the relationship between prevalence and consequence. Because the security significance of a hallucinated name depends on further adversarial and user actions, and its practical significance varies with the role of the referenced package, prevalence alone does not describe practical risk (Section 2.7).

### 2.9.3 Implementation-based rationale for the present study

The limitations identified above do not, of themselves, dictate a single study design. They do, however, indicate the properties that an empirical assessment should possess if its findings are to be interpretable within their scope. The rationale for the present study is therefore implementation-based: it arises from the design choices through which the study responds to these interpretive limitations, and it is stated here at the level of design rather than procedure, with the methodological detail reserved for Chapter 3.

In response to the definitional and classification limitations, the study separates two constructs that the reviewed literature shows can be conflated. Its primary construct is confirmed package-name hallucination, assessed through explicit extraction and normalisation of package references, read-only evidence from the npm registry, and conservative adjudication under which registry absence alone is not treated as sufficient for confirmation. Confirmed package-name hallucination is measured through the primary Package Hallucination Rate (PHR) and Sample Hallucination Rate (SHR). The broader class of exact-name dependency-resolution failures, which is not limited to confirmed hallucinations and may also include, for example, references to removed packages, is characterised separately through the secondary and exploratory Dependency Failure Rate (DFR) and Response Dependency Failure Rate (RDFR). These measures are this dissertation's design; they are not constructs drawn from the prior literature, and DFR and RDFR are not hallucination rates.

In response to the limitations concerning generation conditions and sampling, the study used standardised Node.js/npm coding tasks spanning functional categories, repeated independent generations under frozen model conditions, and a controlled collection protocol, with response evidence retained so that each reported outcome can be traced from the generated response through the extracted reference, registry evidence, and classification to the metric in which it is counted. Grouped comparisons across model conditions and functional task categories are included where the data make them estimable. In response to the distinction between prevalence and consequence, eligible confirmed findings are assessed through a rule-based practical-risk framework defined for this study, which, as Section 2.7.2 noted, draws on the considerations of consequence and detectability but is not a standard derived from the cited literature. The confinement of the study to a single ecosystem responds to the ecosystem-specificity limitation: rather than generalising across ecosystems, it examines one ecosystem under a consistent extraction and validation procedure.

The dissertation does not claim that this combination of elements is unique, nor that any individual element—standardised tasks, repeated generation, registry evidence, adjudication, or rule-based risk assessment—is new. Its rationale lies in bringing these elements together within a single, clearly bounded assessment whose definitions, conditions, and evidential basis are explicit.

### 2.9.4 Statement of the research gap

The research gap addressed by this dissertation may therefore be stated as follows. The reviewed literature establishes package hallucination as a measurable reliability defect with conditional supply-chain significance, and it provides concepts, validation approaches, and empirical precedents on which new work can draw. It also shows that reported findings are bounded by their constructs, validation and classification rules, ecosystems, model conditions, prompts, and sampling designs, and that these differences limit the direct comparison of results across studies. Within this context, there is a need for a clearly bounded and traceable empirical assessment of npm package references in LLM-generated Node.js code that combines standardised tasks, repeated generation under frozen model conditions, a controlled collection protocol, explicit package extraction, read-only registry evidence, and conservative adjudication; that reports confirmed package-name hallucination separately from broader dependency-resolution failure; and that relates confirmed findings to practical risk through an explicitly defined framework.

This gap corresponds to the research questions stated in Chapter 1. The primary prevalence question (RQ1) addresses confirmed package-name hallucination under the conservative construct; the secondary question (RQ2) addresses the broader class of exact-name dependency-resolution failures; the comparative question (RQ3) addresses variation across the evaluated model conditions and functional task categories; and the risk question (RQ4) addresses the practical significance of eligible confirmed findings. The findings that address these questions are bounded by the evaluated tasks, model conditions, collection protocol, and registry state at the time of validation, and they are not presented as estimates for LLM-generated code in general.

## 2.10 Chapter Summary

This chapter has reviewed the literature that provides the conceptual and empirical context for the dissertation. It began with the use of LLMs for code generation and the reliability limitations associated with generated code, showing that code hallucination is recognised as a software-engineering concern, that no single definition is universally adopted, and that the validation method applied determines which errors can be observed. It then examined software dependency ecosystems and package registries, explaining that the resolution status of an external dependency reference is assessed against time-dependent registry evidence, and reviewed supply-chain threats that can operate through package names. Typosquatting, dependency confusion, accidental dependency error, package hallucination, and slopsquatting were distinguished by the origin of the problematic name and by whether adversarial action is involved, and package hallucination was characterised as a reliability defect originating in model output rather than as an attack.

The chapter then reviewed empirical research on package and library hallucination and the approaches through which generated references have been detected, validated, and classified. It showed that registry evidence is a key but time-bounded input and is insufficient on its own to classify a reference, that detection and classification are distinct steps, and that the treatment of confused, removed, local, and unresolved references affects measured prevalence. The review of reliability, security, and risk showed that potential security consequences of a hallucinated reference are conditional on adversarial registration and on the reference being acted upon, and that prevalence alone does not describe practical risk. The comparison of prior studies in Section 2.8 showed that reported findings depend on the models, generation settings, tasks, prompts, ecosystems, and measurement rules of the studies that produced them, so that their figures should not be treated as directly comparable without accounting for those conditions.

From this synthesis, Section 2.9 derived a bounded research gap. The gap is not the absence of prior work on package hallucination, but the need for a clearly bounded and traceable empirical assessment of npm package references in LLM-generated Node.js code, one that separates confirmed package-name hallucination from broader dependency-resolution failure and relates confirmed findings to practical risk through an explicitly defined framework. Chapter 3 describes the methodology through which the study was designed and conducted, including the task set, model conditions, collection protocol, package extraction and normalisation, registry validation, classification and adjudication, metric definitions, analysis procedures, and risk-assessment framework.
